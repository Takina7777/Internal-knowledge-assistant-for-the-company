一、项目启动与总体选型
--------------------------------------------------------------------
目标：企业内部知识问答助手（MVP），基于 LangGraph 开发。

最终定版技术栈：
  - 问答模型   ：deepseek-v4-flash（OpenAI 兼容 API，backend/.env 配置）
  - 向量模型   ：本地 Ollama bge-m3:latest（1024 维，OpenAI 兼容端点）
  - 后端框架   ：Python 3.13 + FastAPI
  - Agent 编排 ：LangGraph（retrieve -> generate -> guard 状态机，token 级流式）
  - 向量库     ：Chroma（本地持久化），预留 Qdrant 抽象层
  - 异步管道   ：Celery + Redis（文档上传异步入库、任务状态轮询）
  - 认证       ：JWT + 本地账号（bcrypt + pyjwt），预留 SSO/OIDC 接口
  - 前端       ：React 18 + TypeScript + Vite + Ant Design
  - 可观测     ：抽象接口预留（noop / Langfuse）
  - 企业微信   ：Phase 2 暂缓，仅留配置占位

用户决策记录：
  - 认证方式     ：JWT + 本地账号，预留 SSO 接口（暂缓 OIDC 对接）
  - 企微机器人   ：暂缓实现，先留 WECOM_* 配置占位
  - Redis 方案   ：用户安装 Docker 后用真实 Redis；无 Docker 期间用 fakeredis 验证

三、遇到的问题与解决（按问题记录）
--------------------------------------------------------------------

【问题 1】venv 创建时 ensurepip 失败：WinError 5 拒绝访问
  现象：py -3.13 -m venv .venv 在 ensurepip 引导阶段报 PermissionError，
        定位到 tempfile 清理临时目录时 os.chmod 被拒。
  根因：DSH 沙箱禁止子进程 os.chmod；CPython 在 Windows 上把
        os.mkdir(mode!=0o777) 映射为"只读属性"，tempfile 用 0o700 创建的
        目录因此带只读属性且无法删除（rmdir EACCES）。
  解决：写入 venv site-packages/sitecustomize.py，让 os.mkdir 忽略 mode
        参数（Windows 上 mode 无实际权限语义），临时目录以默认属性创建。
  结果：pip / pytest / ensurepip 全部恢复正常。

【问题 2】pip install -e . 本地构建失败（Permission denied）
  根因：同上，pip 的 pip-build-tracker 临时目录操作被沙箱拒绝。
  解决：改用 requirements.txt 纯 wheel 安装（不做可编辑安装），
        app 包以源码方式从 backend 目录运行（python -m uvicorn app.main:app）。

【问题 3】npm 安装失败（缓存目录不可写 / 生命周期脚本 EPERM）
  现象：npm 默认缓存 D:\nodejs\node_cache 在沙箱外不可写；
        npm 的 postinstall 脚本 spawn 子进程被沙箱拦截（EPERM）。
  解决：缓存重定向到工作区 .npm-cache；
        npm install 加 --ignore-scripts（本项目依赖无必要脚本）。

【问题 4】前端 vite/esbuild 无法启动（spawn EPERM）
  根因：沙箱禁止"带管道 stdio 的子进程 spawn"，esbuild 必然触发。
  解决：npm run dev / npm run build 需授权全权限运行；
        已验证 vite build（3280 模块）与 tsc 类型检查全部通过。

【问题 5】pydantic-settings 读不到 .env
  现象：从项目根目录运行脚本时提示未配置 LLM_API_KEY，实际已填写。
  根因：.env 默认从"当前工作目录"加载，非 backend 目录运行时找不到。
  解决：config.py 固定从 BACKEND_DIR（配置文件所在目录）加载 .env。

【问题 6】模型误拒（"知识库中没有找到相关资料"）
  现象：文档明明检索到了（5 条引用），模型却回答"无资料"。
  根因：Prompt 拒答规则过于激进，模型过度保守。
  解决：调整 SYSTEM_PROMPT 规则 3——只要检索资料相关就必须回答，
        只有完全无关才拒答。实测 3 个问题全部正确回答。

【问题 7】API Key 误写入 .env.example（安全隐患）
  现象：用户把真实 key 填进了 .env.example（会被 Git 跟踪）。
  处理：恢复占位符 sk-xxx-请填写，并提醒用户轮换 key。

【问题 8】fakeredis 与 kombu 不兼容（EVALSHA）
  现象：Celery worker 启动即崩：unknown command 'evalsha'。
  根因：kombu redis 传输用 Lua 脚本实现未确认消息互斥锁（Mutex），
        fakeredis 不支持 Lua。
  解决：新增 CELERY_DEV_NO_LUA 开关（仅开发环境），将 kombu Mutex
        替换为无锁实现（单 worker 安全）；真实 Redis 必须为 false。

【问题 9】fakeredis RESP3 编码不兼容（BRPOP 协议错误）
  现象：BRPOP 超时返回 b'_'，redis-py RESP2 解析报 Protocol Error。
  根因：fakeredis 2.37 的 TCP 服务器硬编码 Resp3Writer（空值编码为 "_"）。
  解决：scripts/dev_redis.py 启动前把 Resp3Writer 替换为 Resp2Writer。

【问题 10】Celery 任务未注册（Received unregistered task）
  现象：worker 收到任务但报 unregistered，任务被丢弃。
  根因：celery -A app.workers.celery_app 只加载了 app，未导入 tasks 模块。
  解决：celery_app.py 显式 from app.workers import tasks（注册任务）。

【问题 11】docker 命令不可用 + compose 项目名为空
  现象：docker 不在 PATH（用户装在 D:\docker\resources\bin）；
        compose 报 "project name must not be empty"。
  根因：中文目录名"企业知识内部助手"导致 compose 项目名解析失败。
  解决：docker CLI 用全路径（或加 PATH）；compose 文件加顶层 name: ek。

【问题 12】前端提问"无反应"（后端进程消失）
  现象：vite 代理报 ECONNREFUSED 127.0.0.1:8000，提问无响应。
  根因：由 Agent 会话托管的后台进程在轮次结束时被环境回收，
        uvicorn/celery 全部消失，8000 端口无人监听。
  解决：服务必须由用户自己的终端运行（进程才会持久）；
        提供 start_dev.bat 一键启动（后端/Celery/前端三个窗口）。

【问题 13】401 Unauthorized（access token 过期）
  现象：登录数小时后所有请求 401，提问无反应。
  根因：access token 有效期 2 小时，前端未实现自动刷新，
        也未保存 refresh_token。
  解决：前端保存 refresh_token；统一 apiFetch 入口在 401 时自动
        用 refresh_token 换新并重试原请求；刷新失败才登出回登录页。
        （会话最长连续 7 天，期间无感续期）

【问题 14】Celery 连不上 Redis（Error 10061）
  现象：worker 持续重试 connect redis://localhost:6379。
  根因：Docker Desktop 未运行，ek-redis 容器未启动。
  解决：启动 Docker Desktop（容器有 restart: unless-stopped 会自动拉起），
        worker 退避重试会自动重连。

【问题 15】文档状态显示 unknown
  现象：文档管理页所有文档状态为 "unknown"。
  根因：入库时元数据未写 status 字段，前端空值渲染为 unknown。
  解决：tasks.py / ingest.py 补 status="ingested"；
        list_documents 统计 chunk_count，缺失 status 自动补 ingested
        （老文档无需重新入库）；前端加"分块数"列并显示"已入库"。

【问题 16】文档状态 unknown 修复的实际落地（承接问题 15）
  现象：问题 15 记录的解决方式（tasks.py / ingest.py 补 status）与实际
        代码不一致——入库元数据里始终没有 status 字段，文档列表仍全部
        显示 "unknown"。
  根因：修复未真正落到工作区代码（当时在跑的仍是旧副本），列表接口返回
        的元数据缺少 status 与 chunk_count。
  解决：在 ChromaStore.list_documents() 统一落地：按 doc_id 汇总
        chunk_count，并补 status="ingested"（能出现在列表中的文档必然
        已成功入库）；老数据无需重新入库。前端状态列显示"已入库"并新增
        "分块数"列。已实测 4 篇文档全部 ingested/5。

【问题 17】流式问答"没有收到回答，请重试"（SSE 帧分隔符 CRLF）
  现象：无论问什么问题，前端都只显示"没有收到回答，请重试"；控制台无
        报错，Network 显示请求 200 正常。
  排查：后端进程内测试、curl 直连 8000 与经 5173 代理均能收到完整事件；
        用 Node fetch（与浏览器 fetch 同实现）复现，解析到 0 个事件。
  根因：sse-starlette 按 HTTP 行尾规范用 CRLF（\r\n\r\n）分隔 SSE 帧
        （原始字节验证：76 个 \r\n\r\n、0 个 \n\n）；前端 streamChat
        用 indexOf("\n\n") 找帧边界永远匹配不到 → 0 事件 → gotAnswer
        为 false → 显示"没有收到回答"。curl 看似正常只因 CRLF 在终端
        不可见。
  解决：解析前把缓冲区内 \r\n 归一化为 \n 再切帧（兼容跨 chunk 边界）；
        流尾无结束分隔符时兜底解析残留的完整 data 行（防 done 帧被截断）；
        0 事件时抛出明确错误"服务端未返回任何数据"，不再笼统提示重试。

【问题 18】access token 过期后全部请求 401（令牌自动续期缺失）
  现象：登录 2 小时后提问/文档接口全部 401。
  根因：前端只保存了 access_token，从未保存/使用 refresh_token；
        问题 13 所述"统一 apiFetch 自动续期"并未真正落到代码里。
  解决：client.ts 改为双令牌管理（localStorage + 内存）；新增统一
        apiFetch：401 时自动用 refresh_token 换新并重试原请求一次
        （并发 401 只刷新一次）；刷新失败清令牌并回调登出回登录页；
        后端轮换制已实测（旧 refresh token 复用返回 401，契约一致）。

【问题 19】改完前端代码页面行为不变（vite 旧缓存 / 服务跑错目录）
  现象：修改源码并重启前端后，浏览器拿到的仍是旧代码（模块里出现源码中
        不存在的 ApiError），提问依旧"没有收到回答"。
  根因1：当时在跑的服务是从上级目录 D:\桌面\企业知识内部助手\ 的旧代码
         副本启动的（该目录另有一份完整项目），vite 根目录指向那份副本；
  根因2：DSH 沙箱环境下 vite 文件监听失效（touch 文件后仍返回旧转换
         结果），磁盘改动不触发重新转换。
  解决：统一从工作区目录
        D:\桌面\企业知识内部助手\Internal-knowledge-assistant-for-the-company
        启动（start_dev.bat 或手动 cd 到对应 backend/frontend）；
        改前端代码后需重启"前端 :5173"窗口，改后端代码后需重启 uvicorn。

【问题 20】client.ts 编码损坏（vite/esbuild: Unterminated string literal）
  现象：vite 报 client.ts:100:56 ERROR: Unterminated string literal，
        页面模块加载失败。
  根因：排查 vite 监听问题时用 PowerShell Get-Content/Set-Content 读写过
        源码，文件被按系统 ANSI(GBK) 重写，UTF-8 中文乱码并把字符串的
        结束引号吞掉。
  解决：删除损坏文件，用 UTF-8 重新写回，完整链路复测通过
        （登录 → 文档列表 ingested/5 → 提问解析 120 事件 → 回答带引用）。
  教训：含中文的源码文件一律用 UTF-8 编辑工具修改，禁止用 PowerShell
        Get/Set-Content 读写，否则编码会被转成 GBK 损坏文件。


四、优化操作汇总
--------------------------------------------------------------------
  1. 检索链路优化：检索不到即拒答 -> 改为"资料相关必须回答"，消除误拒。
  2. 流式体验：citations 事件先行、token 逐字渲染、SSE 超时保护
     （30 秒无事件自动中止并提示，避免 loading 永久卡死）。
  3. 认证体验：401 自动刷新令牌 + 原请求自动重试（用户无感）。
  4. 幂等入库：ingest 任务先删旧再写新，支持重复执行不产生脏数据。
  5. 环境适配：sitecustomize 补丁、fakeredis RESP2/无锁补丁、
     compose name 固定、requirements 纯 wheel 安装。
  6. 配置健壮性：.env 按 BACKEND_DIR 固定加载，不依赖工作目录。
  7. 安全收敛：.env.example 强制占位符；敏感信息输出脱敏；
     刷新令牌哈希存储 + 轮换（旧 token 立即失效）。
  8. 任务注册显式化、Windows solo 池启动方式，降低运维踩坑。
